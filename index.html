讲者备注 · 01 / Jev：把 AI 判断接进程序

今天我们直接讲 Jev 怎么用。它是 TypeSafe AI 的 System One 模型，可以把一段自然语言里的小判断变成程序能直接接收的标签或数字。比如收到一句“明天下午开会方便吗”，我们不需要一篇分析，只想知道它在约时间。

接下来先看适合什么任务，认识三种输出，然后走完一次 API 请求到程序使用结果的过程，再看几个常见应用。最后用几分钟介绍开源的 Laya。网页上的结果都是教学示例，没有真实调用模型。

02 先判断任务是否合适

像一个会读题的判断函数。

Jev 聚焦“看完材料，做一个明确判断”。TypeSafe 将这种定位称为 System One。

讲者备注 · 02 / 什么任务适合 Jev

可以把 Jev 理解成一个会读题的函数。普通代码擅长处理精确规则，比如两个日期谁更早；但对“这段话是在抱怨还是在请求帮助”，我们往往需要理解意思。Jev 就是用固定接口来做这类判断。

最适合的任务有三个特点：材料给得足够，问题足够小，答案空间能说清。不要把“请分析所有情况并制定最佳方案”当成一个小问题；这种任务更适合拆解，或者交给擅长多步推理的模型。

这里不是说通用大模型不能分类。它当然能，而且结构化输出也是很好的对照。我们关心的是在同样的任务和样本上，Jev 的错误、延迟、费用和维护复杂度是否更合适。

03 先记住三个接口原语

选一个，评一档，判断“是不是”。

Choice / Score / Noul：先确定需要哪种答案，再写问题。

Choice选类别

这条消息主要在说什么？

约时间 / 问进度 / 不明确
约时间
choice = "约时间"

返回选项、各选项概率和 confidence。类别之间没有大小顺序。

Score评程度

这张工单有多紧急？

0 一般 · 1 紧急 · 2 非常紧急
1.8
示意 P = [0.05, 0.10, 0.85]

0×0.05 + 1×0.10 + 2×0.85 = 1.8。是档位的加权期望，不是 180% 的概率。

Noul是否成立

这条反馈提出了具体改进建议吗？

P(yes / true)
0.96
0 倾向否 · 1 倾向是

只针对你问的命题。Jev 的 Noul 没有单独的 confidence 字段。

Score 的档位要有顺序

“一般→紧急→非常紧急”有顺序；“账户→付款→物流”没有顺序，应该用 Choice。

confidence 不是正确率

它由输出概率分布计算。三选一最高概率为 0.96 时，Jev 的 confidence 为 0.94；不代表已证明 94% 正确。

本页数值均为手工构造的教学示例。

资料核对：2026-10-15 · 三种类型 · confidence 定义

讲者备注 · 03 / 三种输出类型

先别记接口细节，只记三句话。Choice 是从明确的选项里选一个；Score 是按有序档位评程度；Noul 是某个命题为真的概率。

Choice 比如消息是约时间、问进度还是不明确。开发者在调用时给出类别和解释，模型返回其中一个类别，以及概率分布。这里的类别不是固定死在模型里的一张总表，我们是在请求里定义这次要问的选择题。

Score 则要特别注意档位含义。一般、紧急、非常紧急分别编号零、一、二。模型为各档位分配概率，再算加权平均，所以能得到一点八。这并不是百分制，也不是违规概率。

Noul 问一个具体的是非题，比如反馈是否提出改进建议。接近零倾向否，接近一倾向是，接近中间则难以区分。Jev 的 Noul 没有额外的 confidence 字段。

最后，confidence 是分布的统计量，不是另一位专家给出的正确性担保。我们依然需要在自己的样本上检查高分是否对应可靠判断。实际接入时，先用最适合任务的类型，不必为了凑齐三个类型而全都用。

04 上手 · 第一步

一条请求，只准备材料和问题。

先在服务端准备 TypeSafe API key，设置环境变量 TYPESAFE_API_KEY，再发送这个请求。

cURL · 可执行请求示例POST /v1/systemone
curl https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
  "model": "jev-1.13.0",
  "state": "明天下午三点开个会，方便吗？",
  "questions": {
    "intent": {
      "type": "choice",
      "instructions": "这条消息主要在说什么？信息不足时选不明确。",
      "criteria": {
        "约时间": "安排或确认见面、会议的时间。",
        "问进度": "询问一件事的当前完成情况。",
        "不明确": "无法明确归入上述两类。"
      }
    }
  }
}'
1

state：给材料

这里是一条消息，也可以是含多字段的 JSON。

2

instructions：把问题说清

写你要判断什么、遇到信息不足怎么办。intent 只是用于对上答案的 ID。

3

criteria：定义选项

选项名称就是返回值；描述说明边界。新增类别时，修改这次请求的定义。

网页只展示代码，不发起请求。真实 key 留在服务端；中文例句的效果需要单独评测。

示例固定稳定版 jev-1.13.0。官方已于 2026-10-14 发布 1.14：当前 jev-preview 指向 1.14.0，jev-latest 仍指向稳定版 1.13.0；别名可能变化。

资料核对：2026-10-15 · HTTP API · 当前版本与别名

讲者备注 · 04 / 发出第一条 API 请求

现在从一个能执行的请求开始。先拿到 TypeSafe 的 API key，放到服务端环境变量，然后向 systemone 这个端点发 JSON。这里没有使用真实密钥，也没有替大家调用接口。

请求里的 state 是被判断的材料，这里就是聊天消息。questions 是问题集合。intent 是我们自己起的 ID，用来在结果里找到对应答案；它本身不参与模型推断，所以真正的问题一定要写进 instructions。

因为我们选择的是 Choice，criteria 就是一张选项表。每个选项都写出含义，尤其要说明什么情况下应该选不明确。这样定义，比只写“请分类”更容易测试和维护。

这个例子固定了稳定模型版本，便于复现实验。最新文档还列出了十月十四日发布的 Jev 一点一四，当前在 preview 别名下，而 latest 稳定别名仍指向一点一三。上线评估应该记录响应里的实际版本，不要让版本悄悄变化。

大家看这条请求就可以开始做第一轮实验，但接口格式正确和中文判断正确是两件事。我们稍后会看怎么评估。

资料核对：2026-10-15 · 响应格式 · 多问题的独立性

讲者备注 · 05 / 程序如何使用答案

上一页发出了问题，这一页看答案怎么接。响应的 answers 下面仍然用 intent 这个 ID，这就是请求和回答的对应关系。choice 返回约时间，概率分布同时告诉我们其他选项的分量。这里的零点九六和零点九四都是手工示例。

右边的代码并不复杂：取出标签，然后从映射表里找到对应的消息队列。Jev 的作用是完成语义判断，程序仍然负责界面、权限和具体操作，不需要模型生成一段流程代码再去执行。

实际系统还要处理超时、限流和异常响应，也要在不确定或信息不足时有回退路径。示例先把主线讲清，不代表已经完整实现了生产服务。

如果需要多个独立判断，可以放在同一次请求里。比如消息类型、紧急程度、是否有具体时间，可以同时问。但它们都独立读取 state，不能让第二题偷偷依赖第一题的答案。需要依赖时，就由应用分阶段调用。

06 Jev 怎么用 · 选一个明确结果

把一段文字，送到正确的下一站。

先定义允许的选项，再让 Choice 判断最合适的一项。程序拿到标签，继续处理。

01 / 客服工单路由

这张工单该谁处理？

输入：“包裹已经收到，但杯子破了，想申请换货。”

问题：售后支持、物流查询、支付问题、不明确，属于哪一类？

返回示意 · Choice
"choice": "售后支持"

接入：把工单送进售后队列，并保留原始描述。退款或换货仍走对应业务流程。

02 / 邮件分类

这是哪一类邮件？

输入：“请确认明天下午的项目会议时间，并补充本周进展。”

问题：工作协作、营销推广、账单通知、不明确，最符合哪一类？

返回示意 · Choice
"choice": "工作协作"

讲者备注 · 06 / 分类与分流 · 2 分钟

这页看三种最容易理解的用法。第一种是客服工单：用户通常不会说“我是售后问题”，而会描述杯子破了、想换货。我们给出有限的部门选项，Jev 选出标签，代码再把工单送去对应队列。

第二种是邮件分类，逻辑完全一样：定义工作协作、营销推广等类别，读取正文，然后返回分类。我们关心的是文字表达的意思。如果只是检查发件人是否在白名单，直接写规则就够了。

第三种是 Agent 选工具。把用户问题和候选工具描述一起提供，Jev 建议选天气查询。请注意，它只是在选择候选工具，真正执行前，程序仍要验证权限和参数。这三种场景的共同点是：选项先定义好，模型负责语义判断，程序负责后续流程。页面中的结果都是教学示例，没有真实调用。

可以请听众想一个自己的分类任务：它有哪些选项？材料不够时，应不应该增加“不明确”？

07 Jev 怎么用 · 给顺序，给信号

除了分类，还能排序与检查。

Score 用有序档位表达程度；Noul 回答一个明确的“是否”问题。不要把所有数字都当成百分制。

01 / 候选文档相关性 · SCORE

哪篇文档更值得看？

输入：问题：“如何重置密码？”
候选文档：“忘记密码后的账户恢复步骤”。

问题：用 0 无关、1 略相关、2 有帮助、3 直接相关，评估这篇文档。

返回示意 · Score
"score": 2.8
0–3 档位的加权期望，不是正确率

接入：对候选文档排序，优先展示更相关的内容。分数衡量相关程度，不等于答案一定正确。

02 / 原文是否支持结论 · NOUL

这句话有材料支持吗？

输入：原文：“基础版导出 CSV，团队版导出 PDF。”
结论：“基础版可以导出 PDF。”

问题：仅依据给定原文，是否能支持这条结论？不判断外部事实。

返回示意 · Noul
"noul": 0.07
倾向“不支持”，不是“没把握”

接入：标记需要复核的结论，并一起展示引用原文，帮助作者修正引用或表述。

03 / 识别改进需求 · NOUL

这里需要补充步骤吗？

输入：一段帮助说明：“要重置密码，请按照相应流程操作。”

问题：这段说明是否需要补充用户能实际执行的具体操作步骤？

返回示意 · Noul
"noul": 0.92
倾向“需要补充步骤”

接入：加入待改进列表，提示作者补充步骤；也可交给通用 LLM 起草，再由作者确认。

↳
Jev 判断“要不要改、哪里需要查”；具体内容由模板、通用 LLM 或人来写。
把改进需求拆成“是否缺步骤”“是否缺示例”等小问题，比一句笼统的“帮我评价”更容易使用。

讲者备注 · 07 / 排序与检查 · 2 分钟

除了选类别，还有两种常见用法。第一种是给候选文档排顺序。先定义从无关到直接相关的四档，Jev 返回一个综合分数。这里的 2.8 来自零到三的有序档位，不是百分制，也不能说明文档里的每句话都正确。

第二种是检查原文是否支持结论。原文说基础版导出 CSV，却有人总结成基础版支持 PDF。我们只问“给定原文支持吗”，示例返回 0.07，意思是倾向于不支持，并非模型不确定。这也不涉及去外部调查产品的真实功能。

第三种是判断哪里需要改进。帮助说明写了“按流程操作”，但没有实际步骤，就可以单独问是否需要补充步骤。Jev 给出信号，程序把文章加入待改进列表，再由作者或通用模型补写。它负责判断需求，不负责生成这篇说明。这几个场景都可以拆小、单独评估，最后由代码组合。

强调三个数字代表不同事情：2.8 是档位期望；0.07 和 0.92 是各自命题成立的概率，不能混用。

讲者备注 · 08 / 日常消息演示

接下来亲手试试消息分类，换成每天都会遇到的聊天消息。我们想自动整理消息，但不需要模型写一大段解释，只需要知道这句话主要是在约时间，还是问进度。于是我们先定义三个选项：约时间、问进度、不明确。

点击第一句，“明天下午三点开个会，方便吗”，页面返回约时间，程序就知道可以放到日程待办这一组。点击第二句，“报告写到哪一步了”，返回问进度，对应进度待办。看第三句，“那个事情，你看一下”，它没有把事情说清，选择不明确，交给人确认更合理。

这就是 Choice 最直观的理解：人先出选择题，Jev 选答案，程序按答案做事。实际 API 还会返回概率等信息，这里先省略。固定选项保证的是输出格式，不保证答案永远正确。迁移到其他场景，只要重新定义材料、问题和选项。

依次点击三条例句，让听众先猜标签。说明此页答案预设，不是真实模型测试。

09 接入前，做这几个小检查

能返回结果，还不等于能放心使用。

用同一批真实任务，对照规则、通用 LLM 和 Jev；再决定把哪个判断接进流程。

01 / 先把题出好

问题小，标准清楚

给足上下文，避免选项重叠。把“信息不足”怎么处理写明，保留边界和反例。

别问“整体怎么样”
改问“是否缺少可执行步骤”
02 / 用自己的样本看效果

看错误，也看概率

固定版本，独立留出测试样本。按语言和场景查看误分、召回、排序效果及高分段的错误。

英文是当前优势语言；
中文任务需要专项验证。

测延迟、吞吐、回退

记录端到端 p50 / p95、输入长度、问题数、重试与人工回退。不要直接照搬别人的倍数。

官方标价 $0.042 / 百万输入 token；
输出免费，外围处理另算。
固定类型减少格式问题，不能消除语义误判。
图片先转成可靠文本；精确计算用代码；把干扰指令、缺证据和长文本放进测试集。

讲者备注 · 09 / 怎样把 Jev 用好

怎么判断值得接入？第一步先把题出好，类别要能区分，信息不足要有出口。很多时候效果问题并不来自模型大小，而是问题太宽、材料不够或人工标准不一致。

第二步用自己的任务测。中文和英文不能直接等同，不同输入长度也可能表现不同。模型返回高概率，不是它一定正确，我们要在成批样本中看高分段是否真的可靠。

第三步看整个流程，既看错误也看代价。不要只看一次最快的调用，要看延迟分布、吞吐、重试以及人工回退。当前官方输入费用很低，但 OCR、检索和人工也会形成成本。

最后，用规则能精确做的事情就用规则。对图片、长文本和对抗指令也要专门检查。我们选择的是适合当前任务的组合，而不是只凭一个新名词替换所有已有组件。

讲者备注 · 10 / 认识开源模型 Laya

最后补充一条开源路线。你提供的文章介绍了 Laya，它由 Convai Innovations 开发，代码和权重公开。它与 Jev 都面向结构化的小判断，但不是 TypeSafe 发布的官方开源 Jev，不能据此推断两者内部架构相同。

用选择题来理解：它把材料、问题和候选选项一起读入编码器，给选项打分，然后整理成标签或数值。它不需要先逐字写出一篇回答，再从回答里解析标签。这是公开架构的简化说明，并不意味着判断一定正确。

文章里的四点二一亿参数主要对应英文模型。中文试验应该先看多语言模型，约三点二二亿参数。默认上下文较短，需要关注文本有没有被截断。它也提供微调路径，不过微调效果仍要用独立测试集确认。

标题中的快四倍很抓眼球，但硬件、输入长度和测试方式不完全一致。我们可以把它看作值得动手测的信号，而不是预先承诺业务一定提速四倍。

from laya import Router
router = Router(device="cpu", max_loaded=1)
result = router.predict(
    "明天下午三点开个会，方便吗？",
    {"intent": {
        "type": "choice",
        "instructions": "这条消息主要在说什么？",
        "criteria": {
            "约时间": "安排或确认见面、会议时间",
            "问进度": "询问一件事的完成情况",
            "不明确": "其他情况或信息不足"

    model="multilingual"
)
print(result["answers"]["intent"]["choice"])

讲者备注 · 11 / Laya 本地接入与选择

动手试用时，先在 Python 三点一零或更高版本的环境安装 Laya。这里固定了核对时的零点四点七版本。第一次预测会联网下载选定模型，之后复用缓存。网页只展示代码，没有下载模型，也没有把预设答案当成真实推理结果。

再看 Python 代码：仍然是同一句消息、同一道 Choice 问题。我们显式选 multilingual，避免中文走到英文模型。CPU 是能起步的运行方式，但实际速度要自己测试；需要加速时再按官方文档配置设备。

最后读取标签，接法和之前相似。但相似的接口不等于行为完全相同，尤其 confidence 的计算方式存在区别，旧阈值必须重新评估。选择托管 API 还是自己部署，主要看任务效果、数据路径、维护能力和整体成本。
